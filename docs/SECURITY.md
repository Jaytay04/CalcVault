# Current security boundaries through Phase 4

CalcVault is not yet a completed vault or an independently audited security product. Phase 2 establishes authentication and session boundaries. Phase 3 establishes the encrypted manifest/object-storage foundation. Phase 4 adds local import, CRUD, preview, and explicit export; encrypted backup and restore remain later work.

The legacy Phase 0 diagnostic still performs authenticated encryption and a protected Keychain read using disposable synthetic values. It remains isolated from enrolled credentials and proves only that those platform primitives execute; it is not the encrypted file format or a backup/restore mechanism.

Enrollment requires an owner-chosen 8–12 ASCII-digit calculator sequence and an independent passphrase. The sequence is stored in its own device-only, unlocked-device Keychain item and is only a navigation secret; it never derives or unwraps the root key. There is no default sequence. From an unlocked private session, the owner can enter the current vault passphrase to replace only this Keychain sequence with 1–12 ASCII digits. A one-digit value is intended for temporary testing: ordinary matching calculations can open authentication, and the shorter sequence is easier to observe or guess. It never bypasses the vault passphrase or Face ID. The owner must change it back explicitly; no automatic expiry exists.

Enrollment generates a random 256-bit root key. The passphrase is interpreted as exact UTF-8 without trimming or case folding, processed with libsodium Argon2id and a random salt at the library's interactive baseline, and used to wrap the root key with XChaCha20-Poly1305. Canonical associated data binds the envelope version, vault identity, purpose, passphrase encoding policy, algorithm, work limits, salt, and biometric setting. Optional Face ID access stores a root-key copy under `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` plus the current-biometric-set policy; successful authentication requires the protected Keychain read, not a separate Boolean biometric check.

Failed passphrase attempts receive best-effort persisted UI delays. This does not prevent offline guessing against a copied envelope and is not described as doing so. Authentication cancellation, lock, or genuine backgrounding revokes the attempt/session and clears the coordinator's retained root-key value. No auto-wipe exists.

The calculator detector accepts only fresh one-at-a-time manual digit events and preserves leading zeros independently of display formatting. Paste, history, results, and imports are excluded. A match is consumed before ordinary equals/history handling, then the visible entry is cleared. The documented recovery route is fifteen taps in the blank top-right calculator navigation area; it still requires the independent passphrase or enrolled biometric path.

The lifecycle controller adds an opaque, static calculator-style cover synchronously on inactive/background notifications. It displays fixed fixture content rather than live calculator state so calculations and navigation digits are not exposed. Revocable sessions, WebKit media shutdown, root-key release, and stale authentication callback rejection are implemented and automatically tested; the updated cover and Face ID races remain physically unverified.

Social views use official HTTPS website destinations, separate persistent WebKit data-store identifiers, and no script-message bridge. Browser-managed state is outside vault encryption. The prototype does not collect credentials, copy cookies, inspect password fields, inject login scripts, spoof a user agent, or expose files/keys to JavaScript.

The encrypted storage format is frozen as version 1 in `STORAGE_FORMAT.md`. It uses a purpose-separated manifest key, a bounded XChaCha20-Poly1305 manifest envelope, and fresh per-revision keys with XChaCha20-Poly1305 secretstream records. A mandatory final tag and bounded framing reject truncation, trailing data, malformed lengths, reordering, duplication, tampering, and wrong keys. Random object identifiers keep private names out of filesystem paths; ciphertext sizes and counts can still be inferred.

Initialization is explicit and recorded independently in a device-only Keychain marker. Once initialized, a missing, corrupt, inconsistent, or wrong-identity vault fails visibly and cannot be interpreted as an empty vault. Repository commits stage and validate ciphertext, publish the object before atomically replacing the encrypted manifest, and recheck the revocable session before publication. Failed migration fixtures preserve the previous directory. These properties have simulator-test evidence, not a formal cryptographic audit.

The external TAR archive reader remains a separate read-only Phase 0 probe. A referenced archive remains authoritative at its independently stored location. Missing, stale, unreadable, or malformed archives fail visibly; none of those states authorizes creating an empty archive or deleting/replacing the original. Plain TAR is packaging/concealment, not encryption.

Phase 4 stages security-scoped and coordinated file-provider reads in chunks, and Photos imports use file transfer representations instead of an unbounded data load. Imports are copies and never authorize deletion of the source. Metadata search runs only against the unlocked in-memory manifest; no plaintext persistent index was added.

Text, image, and PDF previews use explicitly bounded memory paths. Strict mode is on by default and disables video preview. If strict mode is turned off, video playback and explicit export create protected, backup-excluded, randomly named temporary plaintext files. Owned temporary files are removed on dismissal, completion, cancellation, lock, and next launch, but a crash can leave protected plaintext until the next-launch cleanup. Explicit exports can be retained by their receiver and cannot be revoked.

Only disposable synthetic media and archives are suitable at this checkpoint. The Phase 3 initialization/persistence path passed its limited physical-device checkpoint, and Phase 4 passed automated tests plus an unsigned device build, but Phase 4 picker/preview/export/cleanup behavior has not yet been observed on the physical iPhone. Encrypted backup/restore, destructive corruption checks on the installed container, and an independent external security audit are not complete. Do not trust this build with irreplaceable data.
