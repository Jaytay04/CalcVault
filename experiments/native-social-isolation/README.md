# Native social isolation feasibility probe

This disposable probe checks whether the project's pinned Xcode 16.4 toolchain can type-check the public ExtensionFoundation and ExtensionKit interfaces needed for an isolated vault UI on the iOS 18 deployment target. It is not part of the CalcVault app target, contains no TikTok code or IPA, and does not access vault data or website sessions.

Run the manual `native-social-isolation-probe` GitHub Actions workflow. Passing type-checks establishes SDK availability only. It does not establish a working extension, sandbox separation, SideStore signing, App ID cost, or device compatibility. Those require a separately reviewed, synthetic host/extension device prototype before any production integration.

The intended security boundary is a vault process with its own container and no shared App Group with the social host. A native social runtime inside the host must never receive a vault key, a vault file path, or a bridge to the vault UI. Any approach that only patches guest file paths or intercepts APIs while sharing the host sandbox is not sufficient isolation for this vault.

## Xcode 16.4 result (2026-09-25)

Manual workflow run 36185296705 at `d5b13a0` used Xcode 16.4 and the iOS 18.5 simulator SDK, targeting iOS 18.0. Both probes failed to type-check:

- `AppExtensionPoint`: `cannot find type 'AppExtensionPoint' in scope`.
- `AppExtensionIdentity` and `EXHostViewController`: explicitly unavailable on iOS in that SDK.

Therefore this specific custom-UI-extension architecture cannot be built on the pinned toolchain. No host/extension app was built or run; process/container separation was not measured on a device. Apple documents programmatic extension-point generation beginning with iOS 26, but a newer SDK targeting the owner's iOS 18.6 has not been tested here. Do not infer that upgrading Xcode alone will solve it.

LiveContainer is not a substitute for the missing boundary: its own architecture documentation says guests share a sandbox and may read each other's files, and guest extensions cannot be registered. It may reduce installed-app slots, but it does not provide the required vault isolation. Do not place a TikTok IPA into CalcVault's current vault-bearing target.

## iOS 26 runtime and SideStore compatibility (2026-09-25)

The synthetic host installed and launched in an iOS 26.5 iPhone 17 Pro simulator in run 36189086226. Its own status marker reported `Extension discovered`. In run 36190680804, the host's `EXHostViewController` activation callback fired and `SyntheticVaultUI` ran as a separate simulator process. The extension view wrote its marker, but `FileManager.default` resolved its Documents URL to the simulator's top-level `data/Documents`, not a private extension container under `Containers/Data/Application`. The workflow's container assertion correctly failed. A distinct process is established; data-container isolation is **not** established by this unsigned simulator run. These runs also rebuilt the unsigned iPhoneOS target successfully. No physical phone, Apple signing, SideStore refresh, or native TikTok runtime was tested.

SideStore's current [requirements](https://docs.sidestore.io/docs/installation/prerequisites) allow iOS 15 or later, which includes iOS 26; Apple's [compatibility list](https://support.apple.com/en-in/123705) includes the owner's iPhone 16 Pro Max. SideStore [warns](https://docs.sidestore.io/docs/advanced/pairing-file) that an OS update may invalidate its pairing file, so continued operation may require re-pairing. This is separate from whether the experimental extension can be signed.

Source review of SideStore `0.7.0-alpha`'s pinned SideSign revision found that [`AppBundle.loadExtensions()`](https://github.com/SideStore/SideSign/blob/a731c0d5a9a6617c7b385ae493e07ffb7f81cd5d/Sources/Models/AppBundle.swift) scans `PlugIns/*.appex`, while Xcode 26 embeds this ExtensionKit app extension in `Extensions/SyntheticVaultUI.appex` with an extension-point definition beside it. [The signer](https://github.com/SideStore/SideSign/blob/a731c0d5a9a6617c7b385ae493e07ffb7f81cd5d/Sources/CodeSigning/CodeSignerAPI.swift) prepares and assigns extension entitlements via `appBundle.appExtensions`. Thus the currently pinned signer does not enumerate the generated ExtensionKit bundle for independent provisioning/signing. This is a source-level compatibility gap, not a physical install result. Supporting this layout in the signer, or validating another signing path, is required before a one-app native-social design can be considered deployable through the owner's current SideStore release. Do not move the vault into a shared host sandbox to bypass it.

A disposable bundle-placement control in run 36191187524 copied the unsigned simulator app and moved its `.appex` from `Extensions/` to `PlugIns/`, leaving production code untouched. Simulator installation failed with `IXErrorDomain 2` and “Failed to create app extension placeholder.” Merely moving the extension into SideSign's scanned directory is not a viable workaround. The original-layout process activation repeated, and its container assertion again failed.

## Security-boundary and signer follow-up (2026-09-25)

The missing private extension-container path was not merely a file-listing error. A direct synthetic cross-read in run 36192523952 returned `READABLE`: the unsigned simulator host read the extension scene's marker. Run 36192873277 rebuilt and verified both simulator bundles with ad-hoc signatures, then repeated the direct cross-read; it was still `READABLE`. This is a **failed vault-in-UI-extension isolation design in the tested simulator configuration**, not a physical-device result. No real vault data was involved.

Apple's [`EnhancedSecurity` extension-point attribute](https://developer.apple.com/documentation/extensionfoundation/appextensionpoint/enhancedsecurity) was tested as a potential fix. Run 36193290727 failed to compile the ad-hoc-signed enhanced variant with `Attribute: EnhancedSecurity(name: "EnhancedSecurity", value: true) conflicts with UserInterface(name: "UserInterface", value: true)`. Apple's [enhanced-security helper guidance](https://developer.apple.com/documentation/xcode/creating-enhanced-security-helper-extensions) also says those helpers cannot present UI. A protected key in a no-UI helper would still require plaintext to reach the host for rendering, where co-resident native social code could access it; that is not an equivalent vault boundary.

A possible inversion is to retain the vault in CalcVault's main host process and run social code in a separate extension. The direct extension-to-host file-access probe is committed but **NOT RUN**: run 36193740263 did not start either job because GitHub reported failed account payments or a spending-limit restriction. Even a successful reverse file-access result would not prove a standalone TikTok IPA can run inside a UI extension; that binary is an app executable, not an ExtensionKit scene. It would also require the extra extension App ID to be reviewed and signed.

The signer-side change is narrow but independent: SideStore `0.7.0-alpha` aliases `ALTApplication` to SideSign's `AppBundle`; `AppBundle.loadExtensions()` must discover `Extensions/*.appex` as well as `PlugIns/*.appex` so the existing per-extension provisioning and entitlement matching can run. The exact CodeSignKit revision pinned by SideSign (`d0c67710fda9a2646b9e829cb2cf443892728371`) recursively finds `.appex` bundles regardless of their parent directory. This suggests a SideSign discovery patch, not a bundle relocation. No modified signer was built, installed, or tested; changing code in CalcVault alone would not update SideStore's signer on the phone.

LiveContainer documents a way to launch native app guests, but its [architecture](https://github.com/LiveContainer/LiveContainer#how-does-it-work) patches the guest executable, hooks dyld, and calls the guest's `UIApplicationMain`; it also warns that ordinary guests are not mutually sandboxed. Its extension-based multitasking/private-container mode may change the guest-side boundary, but adapting it into CalcVault would be a new architecture using runtime hooks, AGPL-licensed code, and an additional signed extension. That falls outside the current no-private-runtime-hooks and reviewed-App-ID rules. Do not integrate it into the populated vault by assumption.

## iOS 26 synthetic build (2026-09-25)

The separate `project.yml` defines a disposable host app (`org.example.syntheticisolation`) and embedded ExtensionKit UI extension (`org.example.syntheticisolation.vaultui`). Both contain only static synthetic text. Neither target links CalcVault source, holds a real key, runs TikTok, or modifies the shipping `project.yml`.

Xcode 26.6 SDK type-checks the public `AppExtensionPoint` and `EXHostViewController` probes at iOS 26.0; the same probes reject an iOS 18.0 target. Manual run 36187347488 built the **unsigned iOS 26 simulator** host and extension and found exactly one `SyntheticVaultUI.appex` in `SyntheticHost.app/Extensions`. A later run 36187525146 repeated that check and also built an **unsigned arm64 iPhoneOS target** with one embedded extension. This establishes API and bundle-generation feasibility only.

The generated host and extension use two bundle identifiers. Whether SideStore can provision and refresh the extension with the owner's free team—and whether this consumes an additional registered App ID—remains untested. The current production constraint allows only the primary CalcVault identity plus the reviewed recovery/install-check identity; integrating this extension would require a separate App ID review. No signed IPA, SideStore install, device process/container test, native TikTok guest, or vault migration has been performed. Do not alter the populated app on the basis of this experiment.
