# Synthetic native guest feasibility probe

This disposable app contains one SwiftUI screen and a synthetic local-file canary. It does not contain CalcVault source, a vault key, a TikTok IPA, social credentials, network code, or private media. It is **not** a production replacement for CalcVault.

The first question is whether a native app guest can launch and interact in a LiveContainer-style host. The second, separate question is whether a host containing vault plaintext can remain isolated from that guest. Passing the first test does **not** answer the second.

## Pinned upstream reference

Prototype against [LiveContainer 3.8.0](https://github.com/LiveContainer/LiveContainer/releases/tag/3.8.0), source commit `e370a92dfc03ce109ebce00ed4a7cfc64ad1c801`. Its [native guest loader](https://github.com/LiveContainer/LiveContainer/blob/3.8.0/README.md#how-does-it-work) modifies the guest executable and uses runtime hooks; the [LiveProcess extension](https://github.com/LiveContainer/LiveContainer/blob/3.8.0/LiveProcess/Info.plist) is a classic app extension in `PlugIns`, unlike the Xcode 26 ExtensionKit UI extension tested in the adjacent experiment. Do not transfer the earlier ExtensionKit signing or isolation result to this architecture.

LiveContainer's [multitask guide](https://livecontainer.github.io/docs/guides/multitask) lists iOS 16+ and an installation retaining app extensions. Thus an iOS 26 upgrade is not a prerequisite for this *initial* guest-launch probe. The future CalcVault integration, SideStore signing, TikTok compatibility, and actual iOS-version choice remain unverified.

## Build and evidence gate

The manual `native-social-guest-fixture.yml` workflow generates this separate project with XcodeGen 2.46.0 and compiles `SyntheticNativeGuest` for the iOS simulator and unsigned device target. It does not install, sign, or publish an IPA. The separate `native-social-host-simulator.yml` workflow fetches the pinned upstream host, applies a test-only simulator patch, builds an arm64 simulator app, ad-hoc signs it with a synthetic app-group entitlement, stages the synthetic guest, and verifies a rendered guest screen. Neither workflow publishes a device IPA or uses a real social app/account.

Expected guest result: the native button increments once per tap, and the canary reports `Canary round trip passed`. That proves only guest execution and access to its own selected data location. Before adapting the host, use synthetic vault-file and Keychain sentinels to test guest-to-host access, both before and after lock. The security gate fails if the guest can read host plaintext, reach host-only keys, invoke vault operations, or keep the host's private UI exposed on backgrounding. Ciphertext visibility alone is not proof of plaintext compromise, but guest write/delete access still matters for integrity and availability.

The pinned LiveContainer host and `LiveProcess` entitlement templates both request the same 128 Keychain access groups and App Group placeholders. Do not reuse those shared groups for the vault root key or infer isolation from a separate process name. Compare **effective post-signing** entitlements and perform an attempted Keychain read from the guest before any production design is considered.

Public workflow run [36211105254](https://github.com/Jaytay04/CalcVault/actions/runs/36211105254) compiled this fixture for the iOS simulator and unsigned device target with Xcode 26.6. It did not launch a guest, produce a signed IPA, or test isolation. A physical-device trial still needs a separately reviewed signing and App ID plan. Do not remove Spotify, reinstall CalcVault, upgrade iOS, or touch the populated vault for this probe.

Simulator-only host run [36215437291](https://github.com/Jaytay04/CalcVault/actions/runs/36215437291) displayed the synthetic guest screen inside the pinned host. This proves a native guest can render in this disposable simulator setup. The guest's controls were not tapped, its canary was not exercised, and no isolation property was tested. The harness uses a synthetic team/app group and skips an upstream simulator dyld patch that asserted under Xcode 26.6; neither accommodation proves the same loader works on a signed iPhone. The production CalcVault target remains unchanged.

Follow-up simulator run [36217778382](https://github.com/Jaytay04/CalcVault/actions/runs/36217778382) passed guest interaction and its effective-Documents canary round trip, then failed the host-file isolation assertion: the guest read a synthetic sentinel in the host's Application Support directory. This is the security stop for the tested **same-process** launch design. It does not test the separately hosted `LiveProcess` extension, Keychain isolation, signed-device behavior, or a real social app. Do not place CalcVault vault plaintext or keys in a host that executes this guest in-process.

## Unsigned device-signing fixture

The separate manual `native-social-guest-device-fixture.yml` workflow builds the synthetic guest in Release for iPhone using CalcVault's base bundle ID. It invokes the pinned LiveContainer 3.8.0 Mach-O patcher in a simulator host against the unsigned iPhone executable, then packages that prepatched guest as a single-app IPA with `LCPatchRevision=7`. The simulator is only a file-patching tool in this workflow; it does **not** run the iPhone guest. The patch is limited to this experiment and is not applied to production CalcVault. No certificate or signing material enters CI.

[Run 36243145318](https://github.com/Jaytay04/CalcVault/actions/runs/36243145318) passed the configured prepatch checks. Its downloaded 17,695-byte IPA has SHA-256 `f65a255ed589707c6c4e10183417d6579b2676f313af91624b58e9742fdf91d5` and contains no `.debug.dylib` or extension. An earlier Debug artifact was superseded because Xcode placed the Swift app code in a separate `.debug.dylib` while the patch touched only the launcher. The Release result still does not establish that SideStore will sign, export, or install this unusual `MH_DYLIB` main executable, nor that LiveContainer can import or launch it on an iPhone. A signed IPA must stay on the owner's device; do not upload it to this public repository or Actions. Any physical trial must temporarily replace only the disposable Calculator identity, preserve SideStore and Spotify, and have a verified reinstall path first.

The owner subsequently reported that SideStore installed the prepatched fixture but tapping its Home Screen icon immediately returned to Home Screen. This is a **standalone launch failure**, not native guest execution. The main executable's `MH_DYLIB` type is a plausible cause; no crash report was available to confirm it. The next research fixture keeps the main app as `MH_EXECUTE`, and stages a separate prepatched `Frameworks/SyntheticNativeGuestPayload.dylib` for SideStore to sign. Its `LCAppInfo.plist` names that research-only payload; unmodified LiveContainer is not expected to choose it automatically. The signed export, imported-payload launch, and vault boundary still need separate checks.

[Dual-binary run 36258100218](https://github.com/Jaytay04/CalcVault/actions/runs/36258100218) passed its configured build, patch, and package checks. The downloaded unsigned IPA is 33,848 bytes, SHA-256 `1bf01e2d240b23f9998f4a0cea9ccea170a5a75cfaa9fe4e01177ebc54b3b5cd`, matching CI. Source review of the installed SideStore version's pinned signer indicates embedded `.dylib` files are signed recursively, but no signed device output has been inspected. Stock LiveContainer 3.8.0 chooses `CFBundleExecutable`, which remains the standalone main executable; a research-host adapter would need to explicitly select the separate prepatched payload. Neither standalone launch nor in-host guest execution has been demonstrated on a device.

The owner subsequently reported that this revised fixture opens and stays open as a standalone SideStore-installed app. That is a device launch result, not a hosted guest result. The separate `native-social-dual-binary-host-simulator.yml` experiment tests a narrow loader adaptation using a simulator-built copy of the payload. The test-only patch allowlists the fixed payload path inside the staged guest bundle and asks the pinned host to use its existing `LC_MAIN` loader. It does not change production CalcVault, carry a real social binary, or establish vault isolation. The previously observed same-process host-file read remains a security failure regardless of this loader outcome.
